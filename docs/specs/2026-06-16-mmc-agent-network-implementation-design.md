**Status:** Design approved, ready for implementation plan.
**Date:** 2026-06-16

## 1. Scope

Build the **full 10-agent MMC reusable agent network** described in `DEMO_BUILD_HANDOFF.md`, sequenced so a **thin slice is demoable at ~3–4 days** and the **full polished build lands at ~8–13 days**. Add a **plant-cloning capability** (Gate D) that proves a new facility can be added as a copy of Plant 7 with zero orchestrator code changes.

Two scripted scenarios are landed end-to-end for the live demo:
- **Brake-caliper supply disruption** (hero scenario from `DEMO_BUILD_HANDOFF.md` §5).
- **Safety / LOTO incident cluster on L1** — same plant agents, totally different composition, on stage.

This spec does **not** restate architecture, agent rosters, KB→agent mapping, naming conventions, or dataset schemas — those live in `DEMO_BUILD_HANDOFF.md` and `docs/MMC_Plant7_Company_Profile_v1.md` and remain the source of truth. This spec captures only what was added/decided on top of those.

## 2. Decisions captured

| # | Decision | Rationale |
|---|---|---|
| D1 | **Full build, thin-slice first.** | Lets us reach a demoable wow at Gate A before committing to the full surface. |
| D2 | **Reasoning model: configurable with a sensible default.** Default = a GPT-5-class reasoning model; hot-swappable at runtime via env / YAML. | Preserves the "model-agnostic" claim in `DEMO_BUILD_HANDOFF.md` §2; enables a "swap the brain mid-demo" moment. |
| D3 | **Trace surface: both, sequenced.** Foundry portal threads for Gates A–B; custom web trace UI added at Gate C. | Avoids building UI before the orchestrator is interesting; portal is "free" for the thin slice. |
| D4 | **Implementation language: Python.** | Strongest Agent Framework + Magentic story for fast iteration; pandas-native data generation. |
| D5 | **Enterprise data storage: CSV/JSON in repo**, one folder per node, ingested as its own Foundry IQ knowledge source. | Matches existing `kb/` pattern; trivially versionable and reviewable in git. |
| D6 | **Non-KB tool APIs: deterministic stub fixtures.** Each tool is a Python `@tool` function backed by `fixtures/<tool>.json`, keyed by input args, returning canned data or a deterministic "not found." | Reproducible demos, no live-network failure modes, scenario authoring is just fixture authoring. The function body is the only thing that has to change to swap in a real API later. |
| D7 | **Scripted scenarios for the full build: 2** — brake-caliper + Safety/LOTO. | Strongest reuse story on stage ("same agents, different flow") without scenario-rehearsal sprawl. |
| D8 | **All 10 agents are prompt-based Foundry Agent Service agents.** No hand-written agent logic — intelligence comes from prompt + KB grounding + tool bindings + model. Magentic manager is the only piece with real coordination code. | Honest attribution of intelligence to the platform; fast iteration (prompt edit → redeploy → re-run). |
| D9 | **Registry: local catalog file (`agents/catalog.json`) only for the demo build.** Microsoft Agent 365 is the documented end-state and will be added by implementing a second `RegistrySource` against the same interface. A stub `Agent365Source` class with `NotImplementedError` is committed so the seam is visible in code from day one. | Removes Agent 365 access as a prerequisite; "registry-driven discovery" claim still holds against the local catalog. |
| D10 | **Plant cloning content strategy (Gate D): hybrid.** Mechanical clone + ID/date substitution for CSV logs (schemas stay identical); LLM-generated narrative docs (SOPs, manuals) from the new plant's `profile.yaml`. Both gated by `validate_plant.py` for ID format + cross-reference integrity. | Cheap to operate, content reads as genuinely different across plants. |
| D11 | **Plant agents are parameterized from a `plant_profile.yaml` from Phase 1.** Agent cards are generated by `agent_factory.py`, not hand-authored. | Makes Gate D essentially free; no per-plant copy-pasted JSON. |
| D12 | **Build from scratch in a fresh Azure resource group:** `rg-magentictest` in `EastUS`. Nothing reused from any prior demo environment, including the Foundry IQ KB. | Clean slate, no hidden dependencies on prior state, repeatable provisioning. |
| D13 | **Infra-as-code: Bicep.** All Azure resources (Foundry projects, Azure AI Search, Foundry IQ KBs, storage, identities) defined under `infra/bicep/` and deployable to `rg-magentictest` via `az deployment group create`. | Repeatable, reviewable, supports tear-down/rebuild cycles during development. |
| D14 | **Two Foundry projects, split by tier:** `mmc-foundry-plant` (Plant 7 + Plant 4 at Gate D) and `mmc-foundry-enterprise` (5 enterprise nodes). | Realistic governance boundary — plant-floor data and enterprise data have different sensitivity profiles and different stewards in real customers. |
| D15 | **Foundry IQ KB topology:** **1 KB per plant** with 3 sources (mirrors handoff §3 — Plant 7 today, Plant 4 at Gate D). **1 enterprise KB** with 5 sources (one per enterprise node). | The handoff's headline claim is "AI plans the path at two layers — Magentic across agents; Foundry IQ across knowledge sources." Mirroring the multi-source pattern at both tiers gives two distinct places to demonstrate layer 2 (cross-source agentic retrieval). Halves the Search infra vs. one-KB-per-enterprise-node. |

## 3. Demo gates

Each gate is a "could I demo this today" checkpoint that lines up with the phases in `DEMO_BUILD_HANDOFF.md` §6.

- **Gate A — Thin slice (~4–5 days, +1d for from-scratch provisioning).** Fresh `rg-magentictest` provisioned via Bicep (both Foundry projects, Plant 7 KB seeded with 3 sources, identities, Search). Brake-caliper composes a multi-agent flow live, traced via Foundry portal threads. Covers Phase 0 + Phase 1 + 1 stub enterprise agent (Supply Chain) + Magentic happy-path.
- **Gate B — Both scenarios end-to-end (~7–10 days).** All 10 agents present; brake-caliper composes with at least one backtrack; Safety/LOTO composes a distinctly different flow. Covers Phases 2–4 in full (Phase 2 widened to 2–3 days per §8a).
- **Gate C — Polished demo (~9–12 days).** Custom trace UI streaming manager ledgers and agent hops; hot-add of a new agent mid-run; governance overlay (Entra Agent ID per-agent scopes + blast-radius view). Covers Phase 5 + Phase 6.
- **Gate D — Plant cloning (~12–14 days).** Plant 4 cloned from Plant 7 via `scripts/clone_plant.py` + hybrid content generation; brake-caliper re-run produces a different (or cross-plant) composition with zero orchestrator code changes. New work, not in original handoff.

## 5. Orchestration design

**Entry:** `manager.run(problem_statement: str) -> RunResult`

**Discovery:** Manager calls `registry.list_agents()` at start of every run. The active implementation is `LocalCatalogSource` reading `agents/catalog.json`. A `WatchedLocalCatalogSource` variant re-reads the file on every call so a freshly dropped agent card appears without a manager restart — this powers the Gate C hot-add demo.

**Magentic loop:**
1. **Task ledger** — facts + initial plan (candidate agents from the registry).
2. **Progress ledger** — on-track? who next? looping?
3. **Invoke** the next agent via A2A.
4. **Evaluate** response; update both ledgers.
5. **Backtrack** when a step dead-ends (e.g., supplier has no alt-source → re-plan to a different agent).
6. **Stop** when the task ledger says "solved" or a max-step guard fires.

**Model:** any `ChatClient` (Agent Framework SDK). Default = a GPT-5-class reasoning model; overridable via `model_config.py` (env var + YAML). Hot-swap supported between runs.

**Tracing:** every ledger update + agent call emits a structured event consumed by (a) Foundry portal threads (Gates A–B) and (b) the `trace_ui/` SSE stream (Gate C onward).

## 6. Agent design (recap of D8)

Each of the 10 agents is a **Foundry Agent Service agent** defined by:
- **System prompt** — persona, scope, "always cite KB," "never hallucinate facts not in the KB," skill-specific guidance.
- **Tool bindings** — its scoped Foundry IQ KB source(s) via the first-party MCP connector, plus the stub tools in §7.
- **Model** — same default as the manager, overridable per-agent.
- **A2A card** — generated by `agent_factory.py`, published at `/.well-known/agent-card.json`, listing the skills from `DEMO_BUILD_HANDOFF.md` §4. The card is what the registry returns and what the manager reasons over.

No custom Python agent logic. All 10 agents go through the same factory.

## 7. Tool implementations (D6)

- One module per tool family in `src/mmc_agents/tools/` (`capa.py`, `cmms.py`, `erp.py`, `tms.py`, `qms.py`, `lms.py`, `plm.py`, `contracts.py`, `warranty.py`, `demand.py`).
- Each function decorated as an Agent Framework `@tool`; signature mirrors what a real API would expose.
- Body loads `fixtures/<tool>.json` via `fixtures_loader.py`, key-lookups by input args, returns the matching record or a deterministic not-found response.
- Fixtures live next to the data they describe: `enterprise/<node>/fixtures/<tool>.json`, `plants/<plant>/fixtures/<tool>.json`.
- Swap-in for a real API later is a body change: replace fixture lookup with `httpx.get(...)`. The `@tool` signature and the agent prompt do not change.

## 8. Plant cloning (Gate D)

- `scripts/clone_plant.py <source_plant> <new_plant_id> --profile path/to/new_profile.yaml` scaffolds `plants/<new_plant_id>/` from the source plant's structure.
- `scripts/generate_plant_content.py <new_plant_id>` produces content (D10 hybrid):
  - **Mechanical:** copy CSV schemas, substitute IDs (`P7`→`P4`, `L1-PRS-001`→`L1-PRS-401`), shift dates per profile, regenerate row counts from new seeds.
  - **LLM:** generate SOPs, manuals, narrative docs from `profile.yaml` (line mix, equipment, shifts, standards), enforcing naming conventions via post-generation validators.
- `agent_factory.py` regenerates the 5 agent cards for the new plant from the new profile.
- `scripts/refresh_catalog.py` updates `agents/catalog.json`.
- `scripts/seed_foundry_iq.py` creates a per-plant KB (1 KB / 3 sources, matching Plant 7's pattern).
- `scripts/validate_plant.py` enforces ID formats, cross-reference integrity (e.g., every BOM `where_used` references a real line/equipment in the profile), and naming-convention conformance.

A new plant exists when all four pass: scaffolder, content gen, validators, KB seed.

## 8a. Enterprise content generation (Phase 2)

The repo today contains only Plant 7 content. The entire `enterprise/` tree is generated from scratch in Phase 2. Per-node deliverables:

| Node | Structured data (CSV) | Narrative docs (markdown) | Tool fixtures (JSON) |
|---|---|---|---|
| **Supply Chain** | `supplier_master.csv`, `bom_where_used.csv`, `erp_inventory.csv`, `tms_freight.csv` | Supplier qualification policy, logistics SOP, disruption playbook | `erp.json`, `tms.json`, `supplier_master.json` |
| **Procurement & Cost** | `contracts.csv`, `po_spend.csv`, `should_cost_model.csv` | Procurement policy, expedite-cost methodology, supplier-tier definitions | `contracts.json`, `po.json` |
| **Engineering / PLM** | `plm_part_master.csv`, `eco_log.csv`, `effectivity.csv` | ECO workflow doc, part-numbering standard, cross-plant change procedure | `plm.json`, `eco.json` |
| **Enterprise Quality** | `warranty_claims.csv`, `field_failure_feed.csv`, `recall_ruleset.csv` | Warranty handling SOP, recall-threshold policy, cross-plant defect-trend methodology | `warranty.json`, `recall.json` |
| **Demand / Program** | `order_crm_feed.csv`, `program_plan.csv`, `allocation_model.csv` | Launch-readiness checklist, demand-allocation policy, OEM-program definitions | `demand.json`, `allocation.json` |

**Cross-link constraint (must hold for the brake-caliper scenario to resolve end-to-end):**
- `supplier_master.csv` contains a supplier (working name "Acme Brakes") with a 21-day disruption flag.
- `bom_where_used.csv` maps that supplier's part `BRK-CAL-XYZ` to **Plant 7's L1**.
- Plant 7's existing `MMC_P7_PM_Schedule.csv` and `MMC_P7_Incident_Log.csv` contain at least one row touching L1 brake-related equipment so the Plant 7 Maintenance and Quality agents return relevant data when queried with the same part/line context. If they don't today, Phase 2 adds the rows (recorded as a profile change in `docs/MMC_Plant7_Company_Profile_v1.md`).
- Equivalent cross-link audit for the Safety/LOTO scenario.

**Generation approach (mirrors D10 hybrid):**
- **CSVs** — `scripts/generate_enterprise_data.py`, parameterized by a `scenario_seed.yaml` that pins the cross-link facts (supplier name, part number, plant, line). Reproducible by seed; row counts realistic (hundreds–low thousands per file).
- **Narrative docs** — LLM-generated from a per-doc-type prompt template, validated for naming-convention and standards-reference conformance.
- **Tool fixtures** — *derived from the CSVs* by `scripts/derive_fixtures.py`. A tool call like `erp.bom_where_used("BRK-CAL-XYZ")` returns exactly what's in the CSV. Single source of truth, no fixture-vs-CSV drift.

**Validators (run as pytest):**
- Schema conformance per CSV (column types, IDs match naming conventions).
- Scenario cross-link integrity (the constraint above).
- Fixture derivation determinism (running `derive_fixtures.py` twice produces byte-identical JSON).

**Phase 2 estimate:** **2–3 days** for from-scratch generation of all 5 nodes plus the cross-link validation pass — up from 1–2 days in the handoff, which assumed lighter scope.

## 9. Error handling

| Failure | Behavior |
|---|---|
| Agent unreachable (A2A timeout) | Manager logs to progress ledger, marks the agent unavailable for the run, tries an alternate from the registry. If none, returns "no agent could serve X" with the ledgers attached. |
| Stub tool returns "not found" | Treated as a normal tool response; the calling agent decides via its prompt whether to try a different input, escalate, or hand back to the manager. This is what produces the brake-caliper backtrack. |
| KB retrieval returns no hits | Agent responds with explicit "no grounded answer." Prompt rule: no factual claim without a KB citation. |
| Reasoning model errors / rate limits | Manager retries with exponential backoff; falls back to the secondary model configured in `model_config.py` on persistent failure. |
| Manager hits max-step guard | Returns partial answer plus both ledgers so the audience can see why it stopped. |

## 10. Testing strategy

`pytest` suite covering:
- **Fixture determinism** — every stub tool: same input → same output. Critical for demo reproducibility.
- **Schema validators** — `validate_plant.py` runs as a test against every plant under `plants/`.
- **Cross-link integrity** — loads supplier_master, BOM, Plant 7 line/equipment IDs and asserts brake-caliper resolves end-to-end (supplier exists, part in BOM, line in plant profile, matching CMMS/QMS fixture records).
- **Agent card validation** — generated cards conform to the A2A card JSON schema.
- **Orchestrator smoke test** — deterministic (low-temperature) run of brake-caliper asserts the manager hops ≥4 distinct agents and backtracks ≥1 time. Bounds-checking, not DAG-checking.

No tests for prompt content — judged in rehearsal.

## 11. Governance overlay (Gate C)

- Each agent has its own **Entra Agent ID** identity. Access scope (which KBs, which tools, which downstream agents) is exported per-agent to `governance/blast_radius.json`.
- A page in `trace_ui/` renders blast-radius for a selected agent: callers (A2A allow-list), callees (registry-derived), readable KB sources, writable tools (empty set for stub demo).
- **Sensitivity moment:** Plant 7 EHS scoped to a restricted KB source containing one synthetic "confidential" incident; a less-privileged caller cannot elicit it through the manager.

## 12. Out of scope (explicit non-goals)

- Real ERP/CMMS/PLM integrations beyond the stub seam.
- Production-grade auth flows beyond the Entra Agent ID demo overlay.
- Multi-tenant deployment, CI/CD, infra-as-code.
- Web admin UI for editing agent cards (file-based for this demo).
- More than 2 plants. Plant 4 lands at Gate D; further plants are a "you can keep cloning" talking point, not a build deliverable.
